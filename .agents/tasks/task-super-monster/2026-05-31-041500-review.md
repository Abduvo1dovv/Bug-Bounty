# Super Monster: Bug bounty intelligence engine (v1)

A new 12-module Python package (~17k lines) providing post-scan analysis for the Monster web scanner. It consumes Monster's JSON findings, stores them in a local JSON database, correlates findings across targets into attack chains, scores them by a 5-factor weighted formula, generates exploitation playbooks, diffs scan runs, dispatches webhook notifications, and produces JSON/Markdown/HTML reports. The architecture is a linear pipeline with a CLI orchestrating each stage sequentially.

**Watch for:** The retester module makes live HTTP requests to targets with no URL validation—an operator with a malicious database entry could SSRF the host running Super Monster (confirmed). The notification system sends finding details (URLs, evidence, severity) to webhook endpoints with no redaction, so sensitive data flows to third parties unless the operator configures HTTPS URLs (confirmed). The JSON database uses no file locking beyond atomic rename, so concurrent CLI invocations can race on the same `.json` file (likely). There are zero automated tests for any module (confirmed).

## High-level view

The FindingDB handles the critical path—every other module reads from or writes to it—yet its atomic-write strategy (write-temp, `shutil.move`) provides crash safety but no protection against concurrent writers. The retester and full pipeline can run as separate processes against the same database file, creating lost-update races.

The correlator implements 12 chain-detection rules via a graph data structure, iterating findings pairwise within hard-coded caps (10 domains, 3 findings per domain in tech-stack correlation). Large-scale scans will silently truncate correlation results without warning the operator.

The retester makes real HTTP requests using `urllib.request` with rate limiting and timeouts. There is no validation of finding URLs before requesting them—any `file://`, `gopher://`, or internal-network URL stored in the database will be fetched.

The notification system dispatches events to Discord, Slack, Telegram, and generic webhooks. Payloads include raw finding details (evidence strings that may contain tokens, internal URLs, or API keys). The retry logic sleeps synchronously up to 15 seconds per failed webhook, blocking the pipeline.

The prioritizer uses `calculate_priority_score` in config.py with hardcoded fallback values. A separate, more granular scoring table exists in prioritizer.py (`TYPE_EXPLOITABILITY`, `EXPLOITABILITY_FACTORS`), and it's unclear which path the pipeline actually takes—creating ambiguity about what score a given finding receives.

The attack planner generates curl-command PoC templates that embed user-controlled data from findings (URLs, parameters) directly into shell command strings without escaping.

<summary>Issues (7)</summary>

1. **Retester SSRF via unvalidated finding URLs** — The `RetestHTTPClient.get()` fetches any URL stored in the database without scheme or host validation. Restrict to `http://` and `https://` schemes and optionally block RFC 1918 ranges.
2. **Webhook payload leaks sensitive data** — Finding evidence, URLs, and domain names are included in plaintext webhook payloads. Add a redaction layer or at minimum warn operators in documentation.
3. **No file locking on JSON database** — `FindingDB.save()` uses atomic rename but no advisory lock. Concurrent `super_monster` invocations can overwrite each other's changes. Use `fcntl.flock` or equivalent.
4. **Attack planner shell injection in PoC templates** — `TOOL_RECOMMENDATIONS` curl templates use `'{url}'` and `'{param}'` placeholders that are format-string interpolated from finding data without shell escaping. A malicious finding URL could inject shell commands when copy-pasted.
5. **Synchronous webhook retries block pipeline** — `_post_webhook` retries up to 3 times with 5-second sleeps (15s worst case per webhook). With multiple webhooks configured, a single unreachable endpoint can stall the pipeline for 45+ seconds per notification event.
6. **Correlation truncation without warning** — Hard-coded caps in `detect_tech_stack_correlations` and `detect_escalation_paths` silently discard correlation candidates. Operators with large scan datasets won't know they're missing chains.
7. **Zero test coverage** — No unit tests, integration tests, or test fixtures exist. The pipeline handles user-controlled data in security-sensitive ways that need regression coverage.

## Retester as an SSRF vector

The `RetestHTTPClient` in retester.py accepts any URL from the FindingDB and fetches it via `urllib.request.urlopen`. There is no validation that the URL uses an allowed scheme (`http`/`https`) or points to an external host. A finding with `url: "file:///etc/passwd"` or `url: "http://169.254.169.254/latest/meta-data/"` will be fetched when the retest command runs.

The database is a plain JSON file—anyone with write access (or anyone who can inject findings via a crafted Monster report) controls what URLs get fetched from the machine running Super Monster.

```python
# retester.py - no URL validation before fetch
def get(self, url: str, headers: Dict[str, str] = None,
        follow_redirects: bool = True) -> Dict[str, Any]:
    self._enforce_rate_limit()
    # ... directly builds Request(url) and calls urlopen
```

## Webhook notification data exposure

The `_build_discord_payload`, `_build_slack_payload`, and `_build_telegram_payload` methods include `event.title`, `event.message`, `event.domain`, and `event.details` (which can contain evidence strings with discovered tokens, internal URLs, or API keys).

Webhook destination URLs come from environment variables with no scheme or host validation. If an operator misconfigures a webhook URL or an attacker can influence environment variables, all finding data flows to an attacker-controlled endpoint. The `verify_ssl: True` default only validates the remote certificate—it doesn't prevent data from being sent to an unexpected destination.

## Database concurrency gap

The CLI supports running `retest`, `correlate`, and `full` commands concurrently (nothing prevents it), and all modify the same database file. The read-modify-write cycle (`load() -> mutate -> save()`) creates a classic lost-update race:

```python
# finding_db.py save() - no locking
temp_path = self.db_path + ".tmp"
with open(temp_path, "w", encoding="utf-8") as f:
    json.dump(data, f, indent=2, default=str)
shutil.move(temp_path, self.db_path)
```

Two processes calling `load()` at similar times both get the same snapshot, mutate independently, and whichever calls `save()` last wins—silently overwriting the other's changes.

## Shell injection in attack planner PoC templates

`TOOL_RECOMMENDATIONS` in attack_planner.py defines curl command templates:

```python
"curl_template": "curl -s '{url}' --data '{param}=1' OR 1=1--'"
```

These are rendered via string formatting using finding data. A finding with `url = "'; rm -rf / #"` produces a shell command that executes arbitrary code if copy-pasted. The templates should use `shlex.quote()` to prevent accidental injection from findings imported from untrusted Monster reports.

## Correlation engine scaling behavior

The correlator's `detect_tech_stack_correlations` limits analysis to 10 domains and 3 findings per domain:

```python
for i in range(min(len(domain_list), 10)):
    for j in range(i + 1, min(len(domain_list), 10)):
        d1_findings = domain_groups[domain_list[i]][:3]
        d2_findings = domain_groups[domain_list[j]][:3]
```

For an engagement with hundreds of subdomains sharing WordPress, only the first 10 domains (in insertion order—essentially random) get correlated. No warning is emitted. `detect_escalation_paths` has a similar cap at 10 findings per type. These bounds keep runtime tractable but the silent truncation undermines trust in completeness.

## Dual scoring paths

`config.py` defines `calculate_priority_score` (a compact function using small lookup dicts for exploitability and impact). Meanwhile, `prioritizer.py` defines extensive parallel tables: `TYPE_EXPLOITABILITY` (50+ finding types), `EXPLOITABILITY_FACTORS`, `BUSINESS_IMPACT_FACTORS`, `BOUNTY_VALUE_MODIFIERS`. It's unclear whether the CLI's pipeline invokes the config.py function or the prioritizer's more granular engine. If both exist but only one runs, the other is dead code that misleads readers about the scoring behavior.

## Missing test coverage

No test files exist anywhere in the repository. The fingerprint deduplication logic (SHA-256 of `finding_type|url|evidence[:500]`) is the kind of behavior that silently breaks with small normalization changes. The correlation confidence scoring, priority formula, and retest scheduling intervals all have numerical edge cases that would benefit from property-based tests. The retester's HTTP client handles user-controlled URLs in a security-sensitive context with no regression tests guarding against SSRF.
