# Super Monster v2: Active Adaptive Scanner

Complete redesign replacing a 17,444-line passive post-processor (that produced zero useful chains from 957 Monster findings) with a 4,183-line active scanner. The v2 classifies domains by type, selects targeted tests per type, makes real HTTP requests with inline verification, and only reports findings that survive double-checking. The architecture is clean and narrow: classify, scan, verify, correlate, report.

**Watch for:** TLS verification is globally disabled with no opt-in for strict mode (confirmed). The correlator duplicates domain-classification logic instead of reusing the DomainClassifier (confirmed). The `_make_request` helper is copy-pasted across SmartScanner and Verifier with no shared base (confirmed). The session-fixation check has weak detection logic that compares two unauthenticated GET requests and draws conclusions about post-login session rotation (confirmed).

---

## High-level view

The scanner operates a five-stage pipeline: DomainClassifier labels each target (payment, auth, api, admin, cdn, web), SmartScanner runs only the tests relevant to that label, Verifier re-probes each finding with different payloads to filter false positives, SmartCorrelator chains surviving findings into attack paths using seven strict rules, and Reporter buckets results into three tiers (Report / Investigate / Informational) with JSON and Markdown output.

TLS certificate verification is unconditionally disabled in both SmartScanner and Verifier, meaning the tool silently ignores MITM conditions on its own traffic—relevant because it runs from untrusted networks against production targets.

The correlator maintains its own hardcoded domain-type prefix map instead of delegating to DomainClassifier, creating a maintenance fork: if classification rules change in config.py, the correlator's chain decisions will diverge silently. The reporter has a third copy.

The session-fixation test sends two identical unauthenticated GETs and flags unchanged session cookies. This cannot distinguish a properly-issued persistent session from a fixation flaw; the test needs a login-state transition to be meaningful, and its 0.6 confidence will be filtered by the 0.80 threshold anyway—wasting scan time.

## TLS posture and request infrastructure

Both SmartScanner and Verifier construct an `ssl.SSLContext` with `check_hostname = False` and `verify_mode = ssl.CERT_NONE`:

```python
# smart_scanner.py lines 68-70
self._ssl_context = ssl.create_default_context()
self._ssl_context.check_hostname = False
self._ssl_context.verify_mode = ssl.CERT_NONE
```

The same pattern repeats in `verifier.py`. For a bug-bounty scanner running against production targets from potentially hostile networks, this means the tool's own traffic can be intercepted without warning. An `--insecure` CLI flag (default off) would let users opt in when needed for internal targets without degrading the default posture.

The `_make_request` method is duplicated verbatim between the two modules—same error handling, same return signature `(0, {}, "")` on failure. Straightforward extraction into a shared `utils.py`.

## Session-fixation detection flaw

`check_session_fixation` sends two consecutive unauthenticated GET requests and flags session cookies that don't change:

```python
status1, resp_headers1, body1 = self._make_request(url)
# ... no login ...
status2, resp_headers2, body2 = self._make_request(url)
```

Session fixation requires demonstrating that a session ID survives an authentication transition. Two unauthenticated requests proving cookie stability is expected server behavior. The resulting confidence of 0.6 sits below the 0.80 verification threshold, so findings will be filtered—but the test still consumes scan time and rate-limit budget on every auth-type domain.

## Domain classification duplication

Three modules independently classify domains:

1. `domain_classifier.py` — the canonical classifier using `config.DOMAIN_TYPES`
2. `correlator.py` `_get_domain_type()` — hardcoded prefix/keyword maps (75 lines)
3. `reporter.py` `_get_domain_type()` — a third copy

Neither the correlator nor the reporter imports `DomainClassifier`. If a new domain type is added or prefix rules change in `config.py`, the correlator's chain decisions and the reporter's tier bucketing will silently use stale logic.

## Correlator Rule 3 evidence-string semantics

Rule 3 (XSS-to-session-theft) checks `"httponly" in cookie_finding.evidence.lower()` to confirm HttpOnly is missing. The evidence format is `"session_id: missing Secure, HttpOnly, SameSite"`, so the word "httponly" appearing means the flag is absent. The logic is correct but relies on string-contains matching against a formatted message—if evidence formatting ever changes (e.g., to only list the cookie name), this rule silently stops matching.

## Scan orchestration timeout gap

`config.py` defines `MAX_SCAN_TIME = 1800` (30 minutes) but `main.py` never references it. `scan_all_domains` submits all domains to a `ThreadPoolExecutor` and iterates `as_completed(futures)` with no timeout parameter. Individual requests have a 10-second timeout, but DNS resolution via `subprocess.run(["dig", ...], timeout=5)` plus sequential test methods per domain means a large target list with unresponsive hosts could exceed expectations with no circuit breaker.

## CORS verification path specificity

The Verifier's `verify_cors` always tests `https://{finding.domain}/` regardless of the URL where CORS was originally detected:

```python
# verifier.py verify_cors
url = f"https://{finding.domain}/"  # should be: finding.url or fallback
```

If a target reflects origins only on specific API paths but not on the root, verification will fail and a true positive will be dropped. Use `finding.url` as the verification target.

## Test coverage gap

No automated tests exist in the diff—no `tests/` directory, no pytest config, no test files. The untested surface includes:

- Domain classification logic (pure function, trivially testable)
- Correlator chain rules (pure logic given Finding objects)
- Reporter categorization logic
- Monster JSON format parsing (5+ format branches in `_parse_monster_json`)

The correlator gap is the most consequential: incorrect chain logic silently suppresses real attack paths or promotes noise, with no regression safety net.
